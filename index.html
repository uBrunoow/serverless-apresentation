O que é
Definição, componentes e quem é responsável pelo quê.

    

  


  
  

    

      
O que é serverless?

      
Um modelo de computação em nuvem no qual você executa código sem gerenciar diretamente os servidores.

    

    

      
    
        
  • Os servidores existem
    O nome engana: a máquina continua lá, só não é você quem cuida dela.
    • 
        
  • O provedor gerencia
    Manutenção, disponibilidade e escalabilidade passam para a nuvem.
    • 
        
  • Execução por evento
    O código roda quando algo acontece, não o tempo todo.
    • 
        
  • Foco na aplicação
    O time trabalha na lógica de negócio, não na infraestrutura.
    • 
      

      
    

  


  
  

    

      
Componentes e responsabilidades

      
Quem faz o quê dentro da arquitetura.

    

    

      

        
ComponenteResponsabilidade

        
          
EventoDispara a execução: requisição HTTP, upload, mensagem, agendamento.

          
API / GatewayRecebe a requisição, autentica e roteia para a função correta.

          
FunçãoExecuta a lógica de negócio; é pequena, isolada e sem estado.

          
Banco de dadosGuarda o estado da aplicação, já que a função não o mantém.

          
ArmazenamentoGuarda arquivos e mídia, e pode gerar eventos ao receber conteúdo.

          
Provedor de nuvemProvisiona, escala, monitora e mantém toda a infraestrutura.

        
      

      
    

  


  
  

    

      
02

      
Como funciona
Do evento até a resposta, e o que acontece quando chegam mil de uma vez.

    

  


  
  

    

      
Do evento até a resposta

      
Sem nenhum servidor provisionado por nós.

    

    

      

        

        
01
Usuário
Envia a requisição.

        
02
API / Gateway
Autentica e roteia.

        
03
Função
Executa a lógica.

        
04
Banco / Storage
Lê e grava o estado.

        
05
Resposta
Volta ao usuário.

      

    

    
A função só existe enquanto executa: termina o trabalho, o ambiente é liberado.

  


  
  

    

      
E quando chegam mil de uma vez?

    

    

      

        
1requisição simultânea

        
Mil requisições simultâneas viram mil execuções em paralelo, sem nenhuma configuração.

      

      

    

  


  
  

    

      
Quais problemas resolve?

      
A dor operacional de um lado, a resposta da arquitetura do outro.

    

    

      
Gerenciar e manter servidoresO provedor assume a operação

      
Provisionar infraestrutura à mãoRecursos criados sob demanda

      
Picos e quedas no número de acessosEscalabilidade automática

      
Máquinas ligadas e ociosasPagamento pelo uso real

      
Publicar uma funcionalidade novaCiclo de entrega mais curto

    

  


  
  

    

      
03

      
Quando usar
Trade-offs, cenários, ferramentas e um caso real do começo ao fim.

    

  


  
  

    

      
Vantagens e desvantagens

    

    

      

        
Vantagens

        
    
          
  • Menos gerenciamento de infraestrutura
    • 
          
  • Escalabilidade automática conforme a demanda
    • 
          
  • Pagamento baseado no uso, sem recurso ocioso
    • 
          
  • Publicação rápida de novas funcionalidades
    • 
          
  • Foco do time no código e na regra de negócio
    • 
        

      

      

        
Desvantagens

        
    
          
  • Dependência do provedor de nuvem
    • 
          
  • Limites do ambiente de execução (tempo, memória)
    • 
          
  • Cold start na primeira chamada de uma função
            
    
              
    partida fria~800 ms
    
              
    função quente~10 ms
    
            
    
          
    • 
          
  • Depuração difícil em sistemas distribuídos
    • 
          
  • Custo que cresce com o volume de execuções
    • 
          
  • Menor controle direto sobre a infraestrutura
    • 
        

      

    

  


  
  

    

      
Onde faz sentido

      
A pergunta não é se é melhor, e sim em qual cenário as características ajudam.

    

    

      

        
Indicado para

        
    
          
  • APIs e backends de aplicações web
    • 
          
  • Backends de aplicações mobile
    • 
          
  • Processamento de arquivos e imagens
    • 
          
  • Automação de tarefas e rotinas agendadas
    • 
          
  • Sistemas orientados a eventos
    • 
        

      

      

        
Avalie outras opções quando

        
    
          
  • A aplicação precisa de execução contínua
    • 
          
  • É preciso controle fino da infraestrutura
    • 
          
  • O processamento é longo demais para os limites
    • 
          
  • A dependência de um provedor é um risco relevante
    • 
          
  • O volume constante torna o custo por execução alto
    • 
        

      

    

  


  
  

    

      
Tecnologias e ferramentas

      
O papel de cada serviço dentro do ecossistema.

    

    

      
AWS
Lambda
Executa a função em resposta a um evento. É o FaaS mais conhecido.

      
AWS
API Gateway
Porta de entrada HTTP: recebe, autentica e encaminha às funções.

      
AWS
S3
Armazena arquivos e dispara eventos quando recebe conteúdo novo.

      
Azure
Azure Functions
Equivalente da Microsoft para execução de funções por evento.

      
Google Cloud
Cloud Functions
Funções gerenciadas dentro do ecossistema do Google Cloud.

      
Google Cloud
Cloud Run
Contêineres sem servidor, para quando a função pura não basta.

    

  


  
  

    

      
Exemplo prático: upload de imagem

      
O mesmo fluxo da arquitetura, agora com serviços reais.

    

    

      

        

        
01
Upload
O usuário envia a foto pelo aplicativo.

        
02
Amazon S3
O arquivo chega ao bucket.

        
03
Evento
O storage avisa que há arquivo novo.

        
04
Lambda
Redimensiona e gera a miniatura.

        
05
Resultado
Miniatura no S3 e registro no banco.

      

      
    

    
Nenhum servidor ficou ligado esperando o upload. A função existiu apenas durante o processamento, e a cobrança corresponde a esse tempo.

  


  
  

    

      
Conclusão

    

    

      
Serverless troca o controle da infraestrutura por agilidade e escala automática. É uma escolha de cenário, não um upgrade universal.

      
    
        
  1. O provedor cuida do servidor; o time cuida do código e da regra de negócio.
    2. 
        
  2. Resolve ociosidade, picos de acesso e provisionamento manual.
    3. 
        
  3. Cold start, limites de execução e dependência do provedor continuam pesando.
